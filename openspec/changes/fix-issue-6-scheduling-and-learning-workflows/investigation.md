## A. Ranking and priority

**C: Active equations.** `src-tauri/src/algorithms/daqe/terms.rs:93–180` computes `M = .5U + .3O + .2P`. Documents obtain U from `calculate_fsrs_document_priority` (`algorithms/mod.rs:292–372`), not a calibrated forgetting probability. That helper uses its own `Utc::now()`, multiplies due-state bands by `.5 + 1.5*slider/100`, adds stability bonuses `.5/.2` and difficulty bonuses `.3/.1`, then clamps to 10. Thus manual priority occurs in both U and P; clamping makes its effective influence discontinuous and often eliminates the inner distinction. The ranking clock and document helper clock differ.

For overdue documents B decreases from 10 to 5 through day 50, while O grows to 1 at day 14. After O saturates, M can decrease with lateness. No checked source or history evidence establishes an intentional anti-backlog policy or empirical basis for 50/30/20 or 14. Comments describe urgency while implementing decay. The implementation and handbook promise are inconsistent; inferred historical intent is not evidence.

O uses integer days and returns **1 for absent due dates**, despite its “due today” comment. Future and same-instant due dates return O=0. Non-document U prefers retrievability, otherwise estimates `.9^(elapsed/stability)` with elapsed measured **from due date**, rather than last review. Finally both U and P can fall back to `item.priority/10`, counting the same derived scalar twice.

**C: Producers disagree.** `commands/queue.rs:184–408` and `:664–862` build learning-item, extract, video-extract, and document rows. Learning cards omit manual slider/rating despite having those stored fields; their fallback priority is `neutral_queue_priority` (`:586–605`). Text extracts add their manual order-key-derived value to that fallback, but expose no FSRS memory there. Video extracts expose no memory state or manual priority in these rows. Documents expose the slider and memory fields. Playlist rows (`:1058–1090`) resolve a subscription rating through a document helper designed for a different rating scale. Other row types, including audio editions, use fallback data; a missing signal is not verified recall risk.

**C: Composite score and modes.** `models/daqe.rs:242` owns `w_srs*M + w_goal*G + w_energy*E - w_interleave*I - w_friction*F`. Default w_srs is .40. `algorithms/daqe/ranker.rs:87–133` bypasses arithmetic sorting in SRS-only mode and uses the legacy comparator. `algorithms/queue_selector.rs:121–170` buckets due/new/future, then descending priority and due date, using another wall clock. Tie fallback in mixed ranking currently uses input index before ID, so source-order changes can reorder equal-score items. Correcting terms alone will not fix comparator bypasses.

**C: Canonical priority meaning.** `database/priority_rank.rs:1–175` specifies a global ordered queue of documents/extracts/cards: higher order key is more important, slider 0 requests the bottom, 100 the top, displayed percentage comes from rank. Absolute order-key magnitude is not importance. Existing `priority_score` keys, `priority_slider` request snapshots, derived `priority_rating`, and `priority_explicitly_set` must not be treated as four independent preferences. `commands/document.rs:1060`, `commands/learning_item.rs:522`, and the extract priority path already share rank allocation. `resolve_priority_slider` (`algorithms/mod.rs:242`) does not accept the explicit-set flag and treats zero as unset, unlike `usePriorityPopup.tsx:58`. This can lose intentional Lowest values in ranking.

`docs/USER_HANDBOOK.md:661–694` agrees with higher-is-important positional semantics; `docs/product/features/queue/priority-system.md:12,39–45` says the opposite. `src/utils/reviewUx.ts:127–159` also blends rating/tag counts into a separate priority vector and uses derived queue priority as retention risk. Its score feeds session composition (`:193`) and filters (`:353`), not merely a harmless label. The new contract must prevent that path from reintroducing manual priority into temporal risk or reranking an already adaptive-ranked sequence.

**C: Documents retain separate scheduling.** `commands/algorithm.rs:375–470` handles explicit document ratings through `EngagingScheduler`; `algorithms/engaging_scheduler.rs:164–235` uses FSRS memory and bounded engagement modifiers. `algorithms/document_scheduler.rs:90–145` supplies the separate document/extract rotation kernel. Document scheduling is not the flashcard optimizer's review history. Removing ranking micro-bonuses does not imply removing scheduling. Opening/viewing content is not an explicit Again/Hard/Good/Easy assessment. Existing comments mentioning FSRS-6 are stale naming, not proof of the linked kernel version.

## B–D. Card reachability, rendering, editing, and removal

**C: Divergent cloze paths.** `src/utils/cloze.ts:1–64` supports numbered and simplified braces, optional hints, and marker stripping; regexes have different multiline behavior across consumers. `ReviewCard.tsx:244–360` requires `cloze_text`, prefers any nonempty ranges without validating them, then parses markers. `FlashcardScrollItem.tsx:205–313` falls back to question, prioritizes markers over validated ranges, and recognizes legacy brackets. Stored ranges can be stale after a raw-text edit; `InlineCardEditor` updates cloze text without a range-reconciliation contract. No per-cloze-index target exists in the canonical `LearningItem` model: today's renderer hides all deletions together. Per-index sibling creation is not an established promise.

**C: Lossy queue hydration.** `models/queue.rs:6–48` is a queue DTO, not a complete LearningItem; it does not contain interaction metadata or cloze ranges/type. `src/api/queue.ts:63–91` converts it for the frontend.
