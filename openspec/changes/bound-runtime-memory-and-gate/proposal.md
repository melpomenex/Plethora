## Why

On Linux/Kubuntu, Incrementum holds ~2.2 GiB of proportional memory (PSS) with four content tabs open — ~1.08 GiB in `incrementum-tauri` and ~1.23 GiB in `WebKitWebProcess`, almost all of it private anonymous. Worse, closing all four tabs did not release any of it; PSS rose slightly (1.077 → 1.091 GiB native, 1.230 → 1.253 GiB web). Memory that never comes back after a close is a retention bug, not engine overhead, and today nothing in the repository would have caught it: the performance gate (`npm run bench:check`) measures only in-process JS microbenchmark throughput and bundle size, so a multi-gigabyte footprint is invisible to CI and to local verification.

Reading the code already surfaces concrete, citable candidates that fit the symptom (each still has to be confirmed by measurement before it is treated as a cause):

- **No PDF document disposal.** `PDFViewer.tsx` calls `pdfjsLib.getDocument(...)` and `setPdf(pdfDoc)` but never calls `pdfDoc.destroy()` or `loadingTask.destroy()`. Its unmount cleanup (`PDFViewer.tsx:1394-1399`) only flips a `mounted` flag and aborts native range transports. The pdf.js worker keeps a document's parsed structure, font programs, and decoded page data alive until it receives the destroy message, which would explain memory that survives tab close.
- **Whole-file PDF transfer on desktop.** `DocumentViewer.tsx:2097-2110` reads the entire PDF through `documentsApi.readDocumentFile()`, which invokes Rust `read_document_file` (`src-tauri/src/commands/document.rs:1264`, `tokio::fs::read` of up to a 256 MiB desktop cap) and then copies it twice on the JS side (`new Uint8Array(buffer)` in `src/api/documents.ts:366`, then `new Uint8Array(rawBytes)`), before `clonePdfData()` (`pdfLoadSources.ts:13`) makes a third and pdf.js transfers it to its worker. A range-streaming path already exists (`nativePdfRangeTransport.ts`, `get_pdf_document_source_info` / `read_pdf_document_range`) but `shouldUseNativeMobilePdfSource()` gates it to native mobile only. EPUB already streams via the loopback `epub_server`; desktop PDF does not.
- **Four simultaneously live readers.** Incrementum runs a single Tauri window with a single WebView; "tabs" are React subtrees in `TabContent.tsx`. Inactive tabs stay mounted and are only CSS-hidden (`className={isActive ? … : "hidden h-full w-full"}`), so every opened reader keeps its full component tree, canvases, and pdf.js/epub.js instances alive. The resident-tab cap that unmounts least-recently-used tabs defaults to **8** (`tabsStore.ts:328`), so at four tabs it never fires.
- **Unbounded native state.** `EMBEDDING_STORE` (`src-tauri/src/commands/semantic_search.rs:158`) is a process-global `HashMap` of chunks plus `Vec<f32>` embeddings with no eviction; OCR runtimes are pinned in `OnceLock`s; several loopback servers hold per-session state. Whether any of these is actually resident during a plain four-tab reading session is unknown and must be measured.

## What Changes

The work is ordered: **diagnose → fix → verify reclamation → baseline → gate**. No threshold is derived from today's broken numbers.

- **Add a memory benchmark harness** (`npm run bench:memory`): a deterministic scenario driver that launches the packaged/debug Tauri app on Linux, drives a fixed sequence (idle → 1 doc → 2 tabs → 4 tabs → close all → N repeated open/close cycles over one document → repeated cycles over multiple documents → final idle), and samples memory at defined stabilization points. Sampling reads `/proc/<pid>/smaps_rollup` (`Pss`, `Pss_Anon`, `Pss_File`, `Pss_Shmem`, `Private_Dirty`, `Rss`, `Swap`) for the native process, the WebKit web process(es), the network process, and the whole tree. Process discovery is rooted at the launched PID by process group **and** a launch-time marker environment variable, so an unrelated application's WebKit processes can never be counted.
- **Add a documented root-cause investigation** producing evidence for both halves: Heaptrack on the native process across the controlled sequence, and WebKit Web Inspector heap snapshots (A idle / B tabs open / C tabs closed / D after repeated cycles) for the web process, plus an explicit count of how many simultaneous copies a representative PDF has between disk and pixels. Findings are written to `docs/memory-profile.md` and are the gate on which subsequent fixes are justified.
- **Fix reader resource disposal** so closing a document tab makes its resources eligible for reclamation: destroy pdf.js documents and loading tasks, tear down epub.js `Book`/`Rendition`, release canvases and decoded page caches, revoke object URLs, disconnect observers, clear timers, abort in-flight work, and drop any Rust-side per-document state. Only the disposal the investigation shows to be missing is implemented.
- **Stop duplicating document bytes across the IPC boundary** where the investigation confirms duplication: extend the existing native range-transport path to desktop PDFs so pdf.js pulls bounded ranges instead of receiving a whole-file buffer, preserving current Tauri capability/permission scoping and the existing per-document authorization in `get_pdf_document_source_info`. Retain the whole-file path as an explicit fallback for sources the range path cannot serve.
- **Bound live reader residency**: add a separate, much smaller cap for expensive reader tabs (active + a small number of warm readers) alongside the existing generic resident cap, evicting the least-recently-used reader beyond it. An evicted reader is reconstructed on reactivation with its reading position, page/location, and reader settings restored. Tab-switch latency for the warm set is measured, not assumed.
- **Prove repeated use is bounded**: the harness's repeated open/close scenario must show a bounded steady state — a ratchet criterion over the later cycles, not just a peak check.
- **Establish the post-fix baseline empirically**: run the fixed application repeatedly, record variance across samples, and commit representative values for idle / one-document / four-tab / post-close / repeated-cycle-final / scenario-peak, with the hardware, OS, WebKitGTK version, and build profile that materially affect them recorded alongside.
- **Extend the existing performance gate** (`scripts/check-perf-budget.mjs` and its baseline/reporting conventions) rather than building a parallel framework: memory becomes a first-class metric with its own baselines file, combined percentage + absolute thresholds chosen from observed variance, a leak/ratchet criterion, a baseline/current/delta/status table, and machine-readable results. Per the decision recorded in this proposal, the memory gate **hard-fails locally** against a machine-profile-scoped baseline, and runs in CI under `xvfb` as a **non-blocking diagnostic** that uploads its numbers as artifacts — shared-runner memory is too environment-dependent to gate on, while the JS-throughput gate keeps its existing blocking CI job unchanged.
- **Document** the root causes, the architectural changes, how to run the benchmark, how memory is measured, the baseline values, the thresholds, and how to intentionally re-record the baseline.

Explicitly out of scope as "fixes": raising limits, adding swap, suppressing the gate, accepting ~2 GiB as normal, forcing OS memory pressure, manual GC as the primary remedy, restarting WebKit, or discarding tab state. Allocator tuning (e.g. `malloc_trim`, arena limits) is permitted only as defense-in-depth *after* an ownership fix, and only where Heaptrack shows freed-but-retained pages rather than live allocations.

## Capabilities

### New Capabilities

- `reader-memory-lifecycle`: How a document tab acquires, holds, and releases memory — how document bytes reach the renderer, what disposal a tab close performs, how many expensive readers may be simultaneously resident, and what state survives an eviction and is restored on reactivation.
- `memory-benchmark-harness`: The deterministic memory scenario and its Linux process-memory collection — scenario stages and stabilization points, per-process and process-tree PSS accounting from `/proc/<pid>/smaps_rollup`, process-tree discovery that excludes unrelated WebKit processes, and the machine-readable result format.

### Modified Capabilities

- `performance-benchmark-gate`: Add memory as a first-class gated metric — memory baselines and their machine-profile scoping, combined percentage/absolute regression thresholds, a repeated-cycle ratchet criterion, memory rows in the gate's report with baseline/current/delta/status, the distinction between recorded diagnostic metrics and hard gates, a platform abstraction that does not assume `/proc` is portable, and the CI job that records (but does not gate on) memory. Existing throughput-benchmark requirements are unchanged.

## Impact

- **Frontend code**: `src/components/viewer/PDFViewer.tsx` (document/loading-task disposal, page and text cache teardown, desktop range source), `src/components/viewer/DocumentViewer.tsx` (byte-loading path, per-type source selection), `src/components/viewer/EPUBViewer.tsx` (verify `Book`/`Rendition` teardown completeness), `src/components/viewer/PdfPageView.tsx` (canvas release), `src/components/viewer/pdfLoadSources.ts` (drop the extra clone where the range path supersedes it), `src/components/viewer/pdfFeatureFlags.ts` / `nativePdfRangeTransport.ts` (desktop enablement), `src/components/common/Tabs/TabContent.tsx` and `src/stores/tabsStore.ts` (heavy-reader residency cap and eviction), `src/stores/settingsStore.ts` + settings UI (new cap setting), reader position restore paths.
- **Rust code**: `src-tauri/src/commands/document.rs` (range-source authorization reuse for desktop; whole-file path retained as fallback), plus any per-document cache or task lifecycle the investigation implicates. Possible bounding of `EMBEDDING_STORE` (`src-tauri/src/commands/semantic_search.rs`) if it is shown resident during a reading session.
- **Tooling**: new `scripts/memory-bench/` (scenario driver, `/proc` sampler, process-tree discovery), new `scripts/check-memory-budget.mjs` sharing the reporting and exit-code conventions of `scripts/check-perf-budget.mjs`, new `scripts/memory-baselines.json`, new `npm run bench:memory` / `bench:memory:check` scripts, corpus provisioning for representative PDF/EPUB fixtures (not committed as binaries).
- **App instrumentation**: a build-flagged automation surface so the driver can request scenario steps and settle points deterministically instead of synthesizing UI events; it must be absent from, or inert in, release builds.
- **CI**: `.github/workflows/ci-regression.yml` gains a non-blocking Linux memory job (xvfb + WebKitGTK + Rust toolchain + app build) that uploads results; the existing blocking benchmark job is untouched.
- **Tests**: `smaps_rollup` parsing, process-tree discovery and exclusion of foreign WebKit processes, threshold and ratchet-criterion evaluation, reader disposal on close, bounded reader residency, position/state restoration after eviction, repeated open/close lifecycle.
- **Docs**: new `docs/memory-profile.md` (root causes, architecture, how to measure, baselines, thresholds, re-recording protocol); `docs/LINUX_WEBKITGTK.md` updated if a WebKitGTK-specific behavior is implicated.
- **Dependencies**: no new runtime dependencies expected. Heaptrack is a developer tool, not a build dependency. Any driver-side dependency must be dev-only.
- **Risk / compatibility**: the desktop PDF source change alters the load path for every PDF on desktop and must preserve password-protected documents, text selection, OCR, reflow, and outline behavior. The residency cap changes tab-switch behavior for readers beyond the warm set; reading position and settings must survive the round trip. Neither is user-data affecting and neither requires migration.
