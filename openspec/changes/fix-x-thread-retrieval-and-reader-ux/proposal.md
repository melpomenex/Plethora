# Fix X Thread Retrieval & Reader UX

## Why

The previous X-thread change (`tag-editor-readability-and-x-thread-analysis`) marked all its tasks complete, but the runtime feature does not meet the intended result. Two independent failures remain:

1. **Retrieval failure — threads are never actually unrolled.** The Rust backend (`src-tauri/src/twitter.rs`) reconstructs threads from a single X GraphQL `TweetResultByRestId` response, which never contains the conversation timeline the code scans for. Multi-post threads therefore collapse to the single root post. Users see one post, or an error, instead of the full thread.
2. **Presentation failure — the reader is a generic HTML document, not a native Plethora surface.** The thread is rendered as backend-generated inline-styled HTML inside the generic HTML viewer iframe (`DocumentViewer.tsx`), where a scraped-web-article stylesheet neutralizes the thread markup and CSS custom properties never reach the iframe document. The result is the observed white regions, off-center/generic document look, missing thread structure, and poor dark-theme integration on both desktop and mobile.

Meanwhile the root-level reference implementation `xcom.py` demonstrates a mature, working full-thread retrieval strategy — ThreadReaderApp's unrolled-thread surface — that Plethora's Rust backend does not use at all. This is a corrective follow-up: keep everything that genuinely works (URL detection, palette/share routing, AI actions, extracts, flashcards, existing `TwitterThread` model), replace the broken retrieval pipeline and the broken presentation path.

## Current Implementation Diagnosis

1. **URL entry.** X status URLs enter via Command Palette (`src/components/search/CommandCenter.tsx:783-804`), mobile share sheet (`src/hooks/useShareTarget.ts:53-55`), and `useURLMetadata`/`useURLImport` (`src/hooks/useURLMetadata.ts:212-222, 331-350`). URL classification works (`src/hooks/useURLDetector.ts:46-48, 88-112`). All three converge on `useDocumentStore.getState().openTwitterThread(url)`.
2. **Document store.** `openTwitterThread` (`src/stores/documentStore.ts:1130-1250`) has a duplicate-URL guard, calls `documentsApi.fetchTwitterThread(url)` (→ Tauri `get_twitter_thread`), then **immediately persists** via `importTwitterThread` in Tauri mode (L1164), or builds an ephemeral `fileType: "html"` doc with `content: thread.structuredText` and `metadata: { articleHtml: thread.htmlContent, xThread: thread }` (L1188-1194). Note the deviation from the previous design's "ephemeral until learning action" decision — opening a thread writes a permanent DB document right away (acceptable, but must be explicit).
3. **Backend fetch.** `get_twitter_thread` → `resolve_twitter_thread` (`src-tauri/src/twitter.rs:919-1031`): extracts the status id, fetches ONE tweet via GraphQL `TweetResultByRestId` (guest token, `src-tauri/src/twitter.rs:160-251`) or syndication fallback (L254-298), parses a single `TwitterPost` (L665-748), then scans that single-tweet result for `threaded_conversation_with_injections_v2` / `timeline.instructions` (L930-982).
4. **What the backend actually receives.** `TweetResultByRestId` returns `data.tweetResult.result` — a single tweet. The `threaded_conversation_with_injections_v2` timeline exists only in the `TweetDetail` query, which this code never calls. The multi-post branch is dead code; `posts` is always `[root_post]` (L984-993). The task "Implement thread reply traversal" (previous change 2.2) was effectively never implemented — there is no recursive self-reply walking anywhere in the file.
5. **`TwitterThread` production.** `TwitterThread` (L126-139) is produced with `posts.len() == 1` in the multi-post case; `html_content` is built by `build_thread_html` (L761-890) — inline-styled HTML referencing `var(--color-card, #ffffff)`, `var(--color-foreground, #020817)`, etc.; `structured_text` by `build_thread_structured_text` (L893-914), which is solid (`[Post N by @handle]` boundaries).
6. **Document wrapping.** `import_twitter_thread` (L1244-1287) persists `fileType: "html"`, `content = structured_text`, `metadata.article_html = html_content`, `metadata.structured_content = full thread JSON`. `metadata.xThread` is set **only in memory** by the store; `mapDocument` (`src/api/documents.ts:24-30`) never restores it from `structured_content`, so after restart the structured model is gone (AI falls back to `content`, the viewer to `articleHtml`).
7. **HTML display.** `DocumentViewer.tsx` renders HTML docs in a `srcdoc` iframe (L7738-7744, `sandbox="allow-same-origin allow-scripts"`); `htmlSource = metadata.articleHtml || content || htmlContent` (L5056). `injectHtmlViewerStyles` (L5582-5950) injects a stylesheet built for **scraped web articles**: `body * { color/background/font/... inherit/transparent !important }` (L5679-5691) neutralizes the thread's inline styles, generic article typography is re-applied (L5695-5911), a few `.x-*` class rules partially restore thread pieces (L5912-5943). The iframe document defines only `--bg-color/--text-color/--page-border/--page-bg` on `:root` (L5656-5661) — the `--color-*` variables used by the Rust HTML are **never defined inside the iframe**, so every `var(--color-*, <light fallback>)` resolves to the hard-coded light fallback wherever the injected rules don't win.
8. **Why the UX looks wrong.** (a) Most "threads" render one post because of (4). (b) When `htmlSource` is empty for an x.com/twitter.com `filePath`, the viewer shows a fallback error page (L5059-5071) whose inline styles use `var(--color-background, #fff)` and flex-centering — inside the iframe the variable is undefined, so the page is **white with centered text** — the exact reported artifact. (c) When the thread HTML does render, it goes through the generic article pipeline (7): inline styles stripped, no thread spine (`.x-posts-stream` is a plain flex column, L801), every post is a heavy bordered card, generic article `h1/h2/p/img` rules apply, and `body { max-width: 850px }` (L5674) fights the container — "generic webpage/document" rather than a purpose-built reader. (d) Mobile inherits the same iframe path — no dedicated layout at all.
9. **Where ThreadReaderApp should enter.** `xcom.py`'s `thread()` / `thread_summary()` show the reference strategy: one no-auth call to ThreadReaderApp's unrolled-thread surface returns the full ordered thread (text + images per post); X GraphQL is used only for optional enrichment (timestamps, engagement, video, quoted-post detail) and as the single-post fallback. Live verification (see below) shows the JSON route `xcom.py` uses is dead; the ping route and the server-rendered `/thread/{id}.html` page are alive and parseable. The Rust backend should adopt this pipeline.
10. **What can remain unchanged.** `extract_tweet_id` (L145-157), guest-token caching (L160-200), GraphQL/syndication single-tweet fetch (L203-298), all parsers (`parse_post`, `parse_media`, `parse_quoted_post`, `parse_author`), `build_thread_structured_text`, the video import workflow (L1033-1287), frontend URL detection, palette routing, share-sheet routing, `ImportPreview` thread preview, `AssistantPanel` scoped actions, extract/flashcard integration, and the `TwitterThread`/`TwitterPost`/`TwitterAuthor`/`TwitterMedia`/`TwitterQuotedPost` model shapes.

## `xcom.py` Reference Analysis (behavior to port)

- **Full-thread retrieval is ThreadReaderApp, not X.** `XcomClient.thread(tweet_id)` first calls `thread_summary(tweet_id)` (`/api/v0/thread/{id}.json`); if the thread exists it unrolls from that single response (ordered per-tweet HTML content), extracting text (tag-stripped), images (`pbs.twimg.com/media/...` regex), and referenced/status-link tweet ids. Only when ThreadReaderApp has no thread does it fall back to the direct GraphQL tweet.
- **Enrichment is optional and layered.** `fetch_quotes=True` resolves quoted-tweet ids via GraphQL (~0.25s each); `enrich=True` additionally pulls per-post ids from the ThreadReaderApp HTML page (`data-tweet` attributes) and merges GraphQL timestamps/engagement/video/media by index. Enrichment failures are swallowed — the thread still renders.
- **HTML/Markdown generation is a convenience output, not the reading surface.** `thread_html()`/`thread_markdown()` produce self-contained documents (with hard-coded `#15202b` background) for export. The user-visible reading experience in Plethora must be native React, not this HTML.
- **Live verification (2026-08-19) — the port must adapt:** `GET /api/v0/thread/{id}.json` returns `{"status":404,"error":"Not Found"}` for every id tested (including a verified-unrolled 34-post thread and the site's own practice thread, with a browser UA) — the JSON route is dead. `GET /api/v0/ping/{id}.json` is alive: `{"code":200,"pong":"<thread root id>"}` and resolves any in-thread id to the thread root; missing threads return `{"code":404,"message":"Thread not found"}`. `GET /thread/{id}.html` server-renders the full unrolled thread (works for mid-thread ids too): ordered `<div class="content-tweet" data-tweet="{id}" data-screenname="...">` blocks with `<br/>`-separated text and `<span class="entity-image"><a href="pbs.twimg.com/...">` images, plus a `twitter_name`/`twitter_screen_name`/`time` header. No auth, no rate limiting observed (~10 requests). **The Rust adapter must therefore target `ping` + `/thread/{id}.html`, with the JSON contract kept as a compatibility layer (try JSON first, fall back to HTML parsing).**

## What Changes

- **Backend retrieval pipeline (Rust):** replace the dead timeline reconstruction in `resolve_twitter_thread` with a ThreadReaderApp-first pipeline:
  1. `ping` the status id → if a thread exists, resolve the canonical thread root id (`pong`);
  2. fetch `/thread/{root_id}.html` and parse ordered posts (id, text, images, author handle) — one request, no auth;
  3. normalize into the existing `TwitterThread` model (order preserved, no unrelated replies — TRA only contains the authored thread);
  4. optional async per-post X GraphQL/syndication enrichment (timestamps, engagement, video URLs, avatars, quoted-post detail) with bounded concurrency, never blocking the reader;
  5. no thread → fetch the single post via existing GraphQL/syndication path and render as a single-post thread (not an error);
  6. both fail → structured error surfaced natively.
  - Keep `get_twitter_thread` + `import_twitter_thread` command names; add a lightweight `enrich_twitter_thread` command for step 4 and persist the normalized thread so `xThread` survives restarts.
- **Frontend: dedicated native `XThreadViewer`.** `DocumentViewer`/`DocumentViewerWrapper` detects `metadata.xThread` and renders a native React thread reader (author header, thread spine, post cards with media/quotes/actions, skeleton loading, native error states) instead of the HTML iframe. The generated HTML remains only for export/compat, never for the primary display. Mobile gets its own layout (sticky compact header, safe-area padding, bottom-sheet assistant, bottom learning toolbar).
- **One canonical model.** The same normalized `TwitterThread` object (persisted via `structured_content`, restored into `metadata.xThread` by `mapDocument`) drives the viewer, AI context (`resolveTwitterThreadAssistantContext`), extracts, and flashcards. Post ids are stable anchors for AI citations → scroll-to-post.
- **Keep working.** URL detection, palette/share routing, `ImportPreview`, `AssistantPanel` scoped actions, extract/flashcard flows, video import, and the existing model types stay as-is.
- **Sanitization.** ThreadReaderApp HTML fragments are parsed server-side into structured text/media; any rich inline content rendered on the client goes through the project's established sanitizer (DOMPurify, as used in `RichContentRenderer`). No `dangerouslySetInnerHTML` of third-party HTML.

## Capabilities

### New Capabilities

- `x-thread-reader-native`: Presents normalized X threads in a dedicated native Plethora reader (desktop split-pane + mobile bottom-sheet UX) powered by a ThreadReaderApp-first retrieval pipeline with optional X enrichment; one canonical `XThread` model drives viewer, AI context, extracts, and flashcards.

### Modified Capabilities

- `x-thread-analysis`: Retrieval changes from "single-tweet GraphQL reconstruction" to "ThreadReaderApp unroll + enrichment"; thread documents persist the normalized model so `metadata.xThread` survives restarts; AI context and viewer always share the same data.
- `contextual-palette-actions`: Unchanged behavior (X Thread palette action) — verification only.

## Decision: New Change vs. Amend

**Recommendation: create this corrective follow-up change (`fix-x-thread-retrieval-and-reader-ux`) and leave the previous change untouched until this one is implemented and verified.** Rationale: the previous change's tasks are marked complete but its runtime behavior is incorrect; amending would rewrite its task history and blur the audit trail. After this change lands and the visual acceptance criteria pass, archive both changes together (or re-open and amend the old one only if the team prefers a single history line — then the old tasks 2.x/4.x/6.x must be explicitly un-checked). This change deliberately **reuses** the previous change's model types, commands, and frontend routing rather than re-specifying them.
