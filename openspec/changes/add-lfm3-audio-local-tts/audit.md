## Apply baseline and landing decision (task 1.1)

The apply checkout is `main` at the original audit commit. `git status --short` shows no changed tracked application source; the pre-existing notebooklm binary modification and untracked sherpa/whisper binaries are outside this change. The change's planning directory was already untracked when apply began. Accordingly the original source anchors remain applicable.

Rechecked `src/api/tts/types.ts:5,34,91,106`: neither Supertonic nor LFM3 is registered and cancellation/assets/availability extensions remain absent. Supertonic task 7.1 is unchecked; native code presence must not be inferred from its unchecked task list. Rechecked `src-tauri/src/models/hf/hf_client.rs:299`: the revision query-parameter defect remains. `src/services/audio/audioPlaybackRollout.ts:2` still disables global playback, with upstream acceptance tasks 7.1–7.4 and 8.6–8.7 incomplete. `src/components/common/ReaderTTSControls.tsx:941–942` still detaches stale pause/ended handlers.

Landing order: keep Phase 1 outside application source, Cargo/npm dependencies and packaged resources. Only after G1 passes, extend the shared provider contract once while preserving sherpa contracts; then integrate the exact HF pair and independent LFM3 host. Live-reader integration waits for the global owner's desktop parity acceptance, retains its single focus/engine authority and existing epoch/handler protections, and does not enable global/mobile rollout. Do not mark checked planning tasks as hardware evidence or advance dependent production tasks on a partial spike.

## Specifications versus running behavior

Read the canonical `audio-editions`, `audio-edition-generation`, `hf-model-manager`, `document-tts-sync`, `tts-word-boundary-sync`, `tts-exact-start-anchoring`, `audio-edition-position-persistence`, `tts-settings-management` and `audio-editions-in-queue` specs, including scenarios. Their claims about local files, restart resumption and complete chapterization exceed the worker's current implementation. Preserve those product requirements and close their gaps for LFM3. Do not weaken canonical requirements to match today's blobs.

`tts-provider-catalog` is a pending change capability, not a canonical directory. This proposal therefore adds LFM3-specific behavior in `local-lfm3-tts` and modifies actual canonical capabilities. OpenSpec inventory and CLI schema were checked before authoring.

Revision API verification used metadata only: `https://huggingface.co/api/models/LiquidAI/LFM3-Audio-2B-GGUF?revision=plethora-nonexistent-ref-check` returned 200 and current main SHA; the corresponding `/revision/plethora-nonexistent-ref-check` returned 404; `/revision/642697a5597a675cb819ed236ac415c1e60a4f6f` returned that exact SHA. Do not apply this as an unreviewed source fix in a proposal-only task. Add regression coverage for successful non-main lookup and nonexistent-ref refusal when implementing.
