## Why

Plethora was left running overnight (~10+ hours) on a Mac mini (macOS, ARM64, WKWebView via Tauri 2.11.0 / wry 0.55.1). On return, macOS reported a footprint of approximately **74 GB** for the Plethora process tree. This is two orders of magnitude above the ~2 GiB Linux incident that motivated `bound-runtime-memory-and-gate`, it occurred on a platform that change explicitly does not measure (its collector reads `/proc/<pid>/smaps_rollup` and hard-fails as unsupported on macOS), and nothing in the repository today could attribute a single byte of it. Treat it as a release-blocking reliability incident.

We do not yet know whether the 74 GB belonged to the native process, WKWebView WebContent processes, the WebKit networking/GPU processes, the JS heap, Blob backing stores, decoded media, or a combination. What we do have is a code audit that **verified at HEAD** four unbounded-growth mechanisms plus two additional retention vectors, none of which existed in scope of — or were fixed by — `bound-runtime-memory-and-gate`:

- **Unbounded global error history (verified).** `src/main.tsx:91-93` and `src/main.tsx:115-117` push `{ type, message, stack }` onto `window.__plethoraTestErrors` for every `error` event and `unhandledrejection`, in **every build including production**, with no cap and no duplicate aggregation. Introduced 2026-08-23 in 4570af60 (iOS reliability harness) as test-only instrumentation that never got a test-only gate. A repeating error (e.g. a rejection firing every animation frame for 10 hours ≈ 2M occurrences with stacks) grows this without bound.
- **Unbounded global Blob-URL map (verified).** `src/stores/audioEditionGenerationStore.ts:58` is a module-global `Map<string, string>` (`sectionAudioBlobCache`) that accumulates one `blob:` object URL per synthesized audio-edition section (`audioEditionGenerationStore.ts:232`). There is no cap, no eviction, no `revokeObjectURL` on replace (re-synthesizing a section overwrites the entry and orphans the old URL's Blob), no cleanup on edition deletion (`src/api/audioEditions.ts` and the Rust deletion path never touch it), none on cancellation, none on teardown. `AudiobookViewer.tsx:939-960` builds the full section playlist from it, keeping every section's audio alive for the session. Introduced 2026-08-19 (acf89b62, 58fef98e).
- **TTS cache connection and eviction behavior (verified).** `src/utils/ttsCache.ts:26-48` — `openDB()` calls `indexedDB.open()` on **every** cache operation and the returned connection is never `close()`d (`ttsCache.ts:232,258,297,309,326,343`); repeated lookups accumulate `IDBDatabase` connection objects. Worse, `ensureCacheSize` (`ttsCache.ts:175-228`) enforces the 500 MB bound by cursoring the **entire** store and pushing every `cursor.value` — each containing a full `audioData: ArrayBuffer` — into a JS array to compute eviction order (`ttsCache.ts:188`). Eviction is triggered after every over-size put (`ttsCache.ts:283`), so a full cache in steady-state synthesis re-materializes up to the whole cache into JS memory on every put. In WebKit, that ArrayBuffer/Blob churn plausibly ratchets the WebContent footprint via allocator high-water without any live JS leak. Introduced/hardened 2026-08-19 (271115f8; earlier in 0fffab9d).
- **Permanent test heartbeat in production (verified).** `src/main.tsx:580-583` runs a 1-second `setInterval` for the entire app lifetime in all builds, writing `data-plethora-heartbeat` to `<body>`. The bootstrap-phase twin (`src/main-bootstrap.ts:89-102`) correctly stops when startup settles; the main one never does. Not plausibly 74 GB alone, but it is reliability instrumentation doing permanent production work without ownership.
- **Desktop whole-file audio materialization (verified, new finding).** `AudiobookViewer.tsx:1686-1693` — desktop (including macOS) audiobook/podcast playback reads the **entire** file via `readDocumentFile` into an `ArrayBuffer`, wraps it in a `Blob`, and creates an object URL ("Desktop: blob URL is safe (no mobile heap ceiling)"). Mobile already streams through the native media server (`get_media_stream_url`); desktop does not. A single long audiobook is hundreds of MB held simultaneously as ArrayBuffer + Blob + URL, plus whatever WebKit's media stack retains.
- **Scattered object-URL ownership (verified, new finding).** ~40 `URL.createObjectURL` call sites across ~30 frontend files with ~50 corresponding `revokeObjectURL` sites; correctness depends on each call site remembering its pair. Reader TTS does it right (`ReaderTTSControls.tsx:994-996`); the audio-edition path does not; every persistent-cache hit mints a fresh Blob + URL from the stored ArrayBuffer (`src/api/tts.ts:211,217`).

All of these entered the codebase within the last week (2026-08-19 → 2026-08-23), consistent with a fresh regression — but magnitude attribution (which process, which resource category, leak vs. high-water) is still unknown and must come from measurement, not from this list.

### Relationship to `bound-runtime-memory-and-gate`

This is a **follow-up change, deliberately not an amendment**:

- The predecessor is scoped to Linux/WebKitGTK: its collector, process discovery, Heaptrack profiling plan, `xvfb` CI job, and incident (~2.2 GiB PSS) are all Linux. Its unchecked tasks (3.10, 4.x, 5.8, 6.8, 7.3, 7.5, 8.7, 8.8, 9.x, 10.x, 13.1, 14.x) are Linux empirical verification of already-implemented reader fixes — they **remain in the predecessor**, untouched.
- The macOS incident differs in platform, magnitude (74 GB vs 2.2 GiB — likely a different, grosser mechanism), and suspect surface: TTS, audio editions, error instrumentation, and Blob ownership were never in the predecessor's scope, and its scenario stages do not drive them at all.
- Folding six new subsystems and a new platform's measurement stack into the predecessor would produce exactly the incoherent mega-spec this workflow avoids.
- The new change **extends rather than forks** the predecessor's machinery at its designed extension point: `scripts/memory-bench/platform.js` states "a collector for this platform would plug in behind the same scenario, baseline, and gate logic". The scenario driver, settle protocol, corpus provisioning, run-ID marking, result format, and `scripts/check-memory-budget.mjs` comparator are all reused.

## What Changes

Ordered **attribution → bounded resources → deterministic reproduction → evidence-backed fixes → verification → soak → gate**, split into four independently implementable workstreams (see `design.md` D12 for file ownership):

- **WS-A — macOS measurement.** A macOS process-tree memory collector reporting each Plethora-owned process's physical footprint (via a small native helper using `proc_pid_rusage` / `ri_phys_footprint`), normalized into the existing sample/result/baseline shape; platform-agnostic environment collection (`result.js` currently reads `/etc/os-release`, `/proc/cpuinfo`, `/proc/meminfo`); macOS process discovery by ancestry + launch-marker verification with explicit handling of macOS restrictions on reading other processes' environments. The harness's scenario, settle, corpus, and gate logic are unchanged.
- **WS-B — Blob/audio/TTS lifetime.** Bounded, revoking, owner-tagged object URLs for synthesized audio: an explicit LRU cap on `sectionAudioBlobCache` (count + byte caps, revoke on evict/replace, cleanup on edition deletion/cancel/teardown) with a small playback working set; a managed shared IndexedDB connection for the TTS cache; metadata-only eviction (never load `audioData` payloads to pick eviction victims); a streaming (or explicitly capped) desktop audio playback path so whole audiobooks stop being materialized in the WebView heap.
- **WS-C — reliability-instrumentation hardening + resource diagnostics.** Replace the unbounded `__plethoraTestErrors` array with a bounded, duplicate-aggregating recorder (`{ signature, count, firstSeen, lastSeen, sampleStack }`) that is inert in production unless explicitly enabled; gate the permanent heartbeat behind the reliability-harness mode; add a dev/test-only resource-lifetime diagnostic surface (counts and byte estimates: live object URLs by owner, error aggregates, cache entries, in-flight jobs, where practical readers/proxies/connections) exposed as structured data, never as monkey-patched globals in production, and never retaining Blob payloads or user content.
- **WS-D — soak scenarios and the ratchet gate.** New harness stages: TTS synthesize/play/stop cycles, audio-edition generate/play/cancel/delete/retry cycles, and a tiered idle soak (quick 5–10 min / development 30–60 min / nightly 4 h+ / extended 10–12 h+) with periodic sampling throughout; a slope/ratchet evaluation over soak and cycle metrics (post-warmup slope, final-vs-reference delta, per-cycle growth, idle growth/hour, per-process-role splits) that fails a synthetic per-cycle leak even when every peak metric is under its ceiling; scenario-mode-only synthetic-leak injection to prove the gate fails; macOS baseline recording and profile-scoped gating in `scripts/memory-baselines.json`.

Fixes land **after** attribution where evidence matters (WS-B tuning, any newly discovered leak), but the three "correct-by-construction" bounds (error history, blob cache, TTS eviction) are justified by code inspection alone and may land as soon as their WS-C primitives exist. Deep-attribution tooling (Instruments Allocations/Leaks/VM Tracker, WKWebView heap snapshots, `vmmap`/`leaks`/`sample`, allocation generations, named checkpoints A–F) is documented as a repeatable workflow in `docs/memory-profile.md`, which gains a macOS section. A Tauri/Wry/WKWebView control-app isolation experiment is specified as a conditional task, run only if application-level attribution fails to explain the growth; version pins (`tauri = 2.11.0`, `wry 0.55.1`) are respected and no upgrade is proposed.

Explicitly out of scope: redesigning the PDF/EPUB reader lifecycle (the predecessor implemented it; this change only exercises it on macOS and validates convergence), removing legitimate background functionality, allocator tuning without evidence, and any telemetry that ships user content or continuous stack capture in production.

## Capabilities

### New Capabilities

- `resource-lifecycle-diagnostics`: The dev/test-only surface that reports what Plethora itself believes is alive — an owned object-URL registry with per-owner counts and byte estimates, bounded error aggregates, and resource counts for caches, jobs, and in-flight work — and the rules that keep it out of production, cheap, and free of user content.
- `bounded-resource-ownership`: Production invariants for resources that previously had no owner: a bounded and revoking synthesized-audio URL cache, a single managed TTS IndexedDB connection, metadata-only cache eviction, a bounded error recorder, gated test-only timers, and a desktop audio playback path that does not materialize whole files without an explicit bound.

### Modified Capabilities

- `memory-benchmark-harness`: macOS as a supported collection platform (physical-footprint collector, macOS process-tree discovery and role classification, macOS environment collection), idle-soak stages with periodic sampling, TTS and audio-edition scenario stages, and failed-run artifacts sufficient to attribute an overnight soak the next morning. Existing Linux collection and the fixed reader scenario are unchanged.
- `performance-benchmark-gate`: Slope/ratchet evaluation extended to soak and per-process-role metrics on both platforms, a synthetic per-cycle leak that must fail the gate even with passing peak metrics, and macOS machine-profile baselines. Existing comparator behavior and thresholds are unchanged.

## Impact

- **Tooling** (WS-A/WS-D): `scripts/memory-bench/` gains a macOS collector module and a small native helper crate (new files under `scripts/memory-bench/native/`); `platform.js`, `driver.js`, `scenario.js`, `sample.js`, `result.js`, `discovery.js` gain platform branches and soak/TTS stages; `scripts/check-memory-budget.mjs` gains soak/role metric extraction; `scripts/memory-baselines.json` gains macOS profile entries (file created by whichever change records baselines first; entries are machine-profile-scoped so Linux and macOS entries coexist); `package.json` gains soak-tier script variants.
- **Frontend** (WS-B/WS-C): `src/main.tsx`, `src/main-bootstrap.ts` (bounded error recorder, gated heartbeat), new `src/diagnostics/` modules (object-URL registry, error aggregates, resource counts), `src/stores/audioEditionGenerationStore.ts` (bounded cache + lifecycle cleanup), `src/utils/ttsCache.ts` (shared connection, metadata-only eviction), `src/api/tts.ts` / `src/api/tts/providers/shared.ts` (owned URLs), `src/components/viewer/AudiobookViewer.tsx` (streaming/capped desktop playback, playlist from a bounded working set), `src/components/audio/CreateAudioEditionDialog.tsx`, `src/lib/memoryScenario/*` (new scenario ops).
- **Rust**: none required in the shipped app. The macOS footprint helper is a standalone build tool invoked by the driver, not linked into the app; existing commands (`get_media_stream_url`) are reused for desktop streaming. Stale `INCREMENTUM_MEMORY_*` comments in `src-tauri/src/commands/memory_scenario.rs` and `src/lib/memoryScenario/config.ts` are corrected (the constants themselves already read `PLETHORA_MEMORY_*`).
- **CI**: an optional non-blocking macOS soak job (GitHub Actions `macos-14` runner, nightly tier) recording results as artifacts; no change to any blocking job.
- **Docs**: `docs/memory-profile.md` gains the macOS incident section (verified findings, reproduction, attribution, fixes, before/after, accepted high-water behavior, machine profile, limitations) and the Instruments/WKWebView manual workflow.
- **Dependencies**: no new runtime dependencies. The native helper uses macOS system APIs (`libproc`) only.
- **Risk / compatibility**: playback of generated audio editions must remain seamless across section boundaries under the working-set design (prefetch, not revoke-under-playback); TTS cache migration must not invalidate existing cached audio; the error recorder must remain readable by the iOS reliability harness (its consumer contract moves from an array to an aggregate API); streaming desktop playback must preserve position persistence and remote-URL fallback. No data migrations; no scheduling-semantics changes; Tauri pins untouched.
