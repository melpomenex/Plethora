## Qualification scope

These figures are proposed acceptance thresholds. Local Chromium worker/player evidence and seeded pure-TypeScript benchmark measurements are recorded in `decoder-probe-results.md`. Packaged WebView timing, power, cross-platform compatibility and 30-minute sustained playback measurements have not been completed, so these results do not qualify a release target.

An active 1920×1080 RGBA buffer uses 7.91 MiB. One hundred such buffers would use roughly 791 MiB if retained simultaneously. Browser GIF or video decoders may use a different buffer strategy. The import worker retains a logical screen of at most 7.91 MiB, at most one restoration region of the same size, one indexed patch and LZW scratch, one small palette sample, and bounded encoder scratch. Source and compressed output pools are separately bounded. A 518,400-pixel desktop rendition costs about 1.98 MiB for one RGBA buffer and a 230,400-pixel mobile rendition about 0.88 MiB. A canvas plus two decoded buffers costs about 5.93 MiB desktop or 2.64 MiB mobile before poster, compressed bytes, browser caches, transient copies and compositor surfaces. Device-pixel-ratio caps on the canvas do not constrain the WebView's offscreen blur allocation.

## Fixtures and instrumentation

Use small synthetic decoder fixtures with literal expected pixel rectangles, delays and cycles. Include 87a stills, 89a animation without repeat metadata, finite and infinite repetitions, local/global tables, interlace, transparency, display area smaller than logical screen, disposal 0–3 and restoration chaining, and zero/10 ms timing. Compare full decoded presentation frames and timeline against an independent fixture oracle. Include malformed headers/tables/codes, invalid sub-blocks and offsets, truncated streams, corrupt LZW with valid structural preflight, unsupported rendering blocks, untrusted thumbnails and expired save generations.

| Performance fixture | Use |
| --- | --- |
| Small 480p, short, low cadence | Representative easy import and repeated save/switch test. Include localized motion. |
| Medium 720p, six seconds, variable timing | Main performance reference. Include high motion and a mostly static counterpart. Keep logical pixel work below the import ceiling. |
| Large 1080p, many partial updates | Exercise downsampling and near-boundary composition. Include one fixture inside and one above the total-work cap at equal dimensions. |
| Extreme 4K or highly compressed many-frame file | Verify rejection from header/budget accounting, no large decoded allocation, and responsive cancellation. |
| Long holds, rapid transitions, alpha, scene changes | Verify duration-weighted palette and pacing across clear/restore frames and wrap seams. Include near-threshold flash and clearly unsafe looping fixtures. |

Use real shell routes for rendering tests. Add representative animated and static screenshot fixtures with a fixed presentation time, test contrasting bright/dark checkerboards and red/high-contrast flash patterns, and capture protected surfaces in light and dark variants. Verify EPUB pages and toolbar, fixed/reflow PDF, Markdown, themed HTML and the article reader, assistant panel, Study Plans, guided trails, assessments, reading queue and navigation, dialogs and popovers on wide and compact layouts. Check normal/mobile navigation, keyboard focus, forced/OS motion settings and e-ink. Verify reduced motion before the first animated paint.

For local pure-function benchmarks, use seeded data through `src/test/bench-support.ts`, a module-level result sink and `src/**/*.bench.ts` suites for preflight, temporal selection and histogram finalization. Use fresh deterministic inputs of known size. Establish anchor-normalized baselines in `scripts/perf-baselines.json` and run `npm run bench:check` and its bundle budget checks. Check lazy worker bytes and default shell loading separately. Browser/packaged measurements use actual on-disk fixtures, an empty and a warm storage state, activity traces and device instrumentation. The Vitest gate cannot measure compositor costs.

Record environment, OS and WebView versions, package type, compositor mode, GPU driver, display size/DPR, renderer policy and temperature. Use at least five imports per fixture on each reference device and record every trace. Use 20 operations for switch/pause latency quantiles. Record median import per reference fixture and its worst run. Trace change callbacks, requested and presented frame counts, stale draws, long tasks, background cleanup and worker lifetime. Use DevTools or process sampling for CPU and memory, Android Perfetto and battery instrumentation, Apple Instruments or platform energy tools where available. Separate app-owned buffers from process RSS and compositor memory. A canvas paint timestamp describes the application's submitted frame. Where presentation, decode, GPU or energy counters are unavailable, use external tracing where possible and mark missing fields.

## Initial release gates

| Metric | Starting threshold and measurement |
| --- | --- |
| Preparation | Medium fixture median first poster within 2 s on reference desktop, 4 s on mobile. Measure complete analysis and preview readiness separately. Median full preview within 4 s desktop or 6 s mobile. Reference preflight plus analysis within 4 s. The wall-clock worker watchdog is 10 s for all accepted imports. A budget-exceeded still outcome must be explicit and cancellable. |
| Responsiveness | On supported targets, no import-attributable main-thread task ≥50 ms and p95 input-to-next-paint during the exercised settings interaction ≤100 ms and within 20 ms of matched still baseline. Trace the main-thread encode fallback separately. Reference loading starts on explicit user input and must not increase the normal startup chunk. |
| Presentation | Minimum actual draw interval ≥50 ms desktop or ≥83.33 ms mobile, ignoring the first frame. With a continuously changing fixture in a healthy foreground tier, ≤10% of scheduled source-frame changes missed, and p95 late presentation within one tier interval. Long authored holds are not drops. On resize, only CSS dimensions change unless a real rendition changes. |
| Suspension and switching | No new media decode or presentation scheduling after the policy closes. No stale paint. Poster or safe theme fill is available by the next paint after disable/theming switch. p95 time from focus restoration to eligible animated paint ≤250 ms on a warm saved asset. Permit one already-issued engine decode to settle with immediate cleanup. |
| Owned resources | One current owner, at most one decode in flight, at most two decoded playback frames and one canvas, zero outstanding owned decode jobs or display callbacks after teardown. Check object URLs, worker terminations, bitmap closes, listener cleanup and registry/asset references instrumentally over 50 switches. After warm-up and collection, investigate sustained browser/content process RSS growth >5 MiB over the last 20 min. Confirm the heap and asset counters return to the idle range after teardown. |
| CPU and power | On a matched still-vs-moving trace with a typical eligible frame pack, initial p95 steady CPU delta ≤20 points desktop and ≤15 points mobile when normalized to one fully occupied logical core, including the browser/compositor processes when separable. For eligible sustained playback, target energy ≤15% over still baseline on representative desktop and mobile. Compare repeated 30-min paired runs with fixed brightness and sustained thermal conditions. Report instrumentation error and uncertainty. On targets with no reliable power meter, require thermal/CPU evidence and record the missing metric. Treat thermal throttling or lag as a failure even if the CPU delta appears low. |
| Software and blur fallback | Compare blur at 0/default/cap plus protected surfaces, high DPR, resizing and software rendering. Prefer the smallest viable CSS change. If default blur misses a gate, reduce its effective cap or choose still backing. If no animation treatment meets the gates, the release target uses the poster. |

Sample pacing only during changing content. Two consecutive five-second foreground windows with ≥12 due changes each and >20% missed deadlines step requested cadence down once to 10 fps desktop or 6 fps mobile with the same wall-clock timeline. Evaluate again after ten foreground seconds. Persistent overshoot causes poster fallback for the session. Discard sampling on lifecycle pauses, do not step quality back up automatically, and expose the fallback reason. A new explicit selection can retry. This controller uses scheduling evidence only. Use device measurements to decide rollout and any change to the initial budgets.

## Platform evidence and fallback

Tauri uses its host WebView. Browser and Playwright tests cover deterministic logic and screenshots, but a packaged release requires an actual host runtime. Run the same Worker/CSP, canvas, IndexedDB commit/restart, still-format encode/decode round-trip, power, lifecycle, and console-error checks on each platform. For playback qualification use standard and software GPU modes where applicable, then repeat a hidden/focus transition with queued work, native minimize, mobile background and foreground, temporary suspension, and a cold reload with an intentionally missing pack.

| Target | Validate on real builds | Main risks and fallback |
| --- | --- | --- |
| Linux / WebKitGTK | Prioritize AppImage and Debian release packaging. Cover Wayland and X11, supported old and current WebKitGTK, one hardware mode and forced software, and a machine with constrained or disabled DMABUF. Inspect `src-tauri/src/graphics.rs` and `src-tauri/src/linux_runtime.rs` when comparing package behavior. | GPU policy can disable hardware acceleration/compositing or alter DMABUF. Still-frame decode avoids relying on installed GStreamer video plugins. Full-window blur can still be software-composited. [WebKitGTK multimedia](https://docs.webkit.org/Ports/WebKitGTK%20and%20WPE%20WebKit/Multimedia.html) |
| macOS / WKWebView | Apple Silicon with the minimum supported and a current OS. Check whether Worker canvas + `convertToBlob` actually works for formats used, verify background resume and disclosed settings, and measure CoreAnimation layer cost. | Use bounded scratch encode when qualified and poster on failed runtime probes. Video hardware capability is useful for a future candidate only. [WebKit OffscreenCanvas notes](https://webkit.org/blog/14205/news-from-wwdc23-webkit-features-in-safari-17-beta/) |
| Windows / WebView2 | Packaged build on an integrated GPU, with native window minimize/focus, high DPI and software acceleration disabled/enabled for comparison. Record the installed runtime version. | Browser decoding success does not guarantee inexpensive compositing or timely frame upload. A future video capability probe needs actual MP4/WebM playback. [WebView2 runtime overview](https://learn.microsoft.com/en-us/microsoft-edge/webview2/) |
| Android / System WebView | Packaged release on at least one low/mid-tier phone, SAF file chooser and drop path where available, disabled-by-default fresh profile, charging opt-in, battery saver, thermal fallback, task switching and screen lock. Compare the provider's battery status with device state. | Current command gives placeholder charging and saver data. Wire the existing Kotlin query and prove accuracy or use the poster with unknown power. Record WebView provider and version. [Android framework format support](https://developer.android.com/media/platform/supported-formats) |
| iOS / WKWebView | Where a supported build is available, test low memory, Files selection, plug/unplug and Low Power Mode, foreground/lock, Worker and bitmap support and scrolling inside the compact sheet. | OS updates couple WebKit and decoder changes. Poster-only when lifecycle or playback gates are unverified. A future video path needs inline muted behavior in the app configuration. [WKWebView inline playback configuration](https://developer.apple.com/documentation/webkit/wkwebviewconfiguration/allowsinlinemediaplayback) |
| Browser / PWA | At minimum automated Chromium and WebKit smoke, plus a representative deployed browser and compact mobile browser. Test storage access, focus/visibility ordering, reload and quota. | Do not infer mobile Tauri capabilities from responsive layout or a user agent. Unknown power state is reported, and mobile shell caps apply. [Tauri WebView versions](https://tauri.app/reference/webview-versions/) |

Run 30 minutes of animated playback and 30 minutes of corresponding still playback on representative desktop and native mobile devices, with equivalent scripted scrolling and idle segments. Repeat each pair against cold and thermally stabilized systems as practical. Check stalls, repeated rebuilds, delayed input, memory growth, GPU saturation, thermal state and energy. The poster-only state and hidden window should approach the matched idle state. Inspect cancellation/re-entry immediately after the run. If device access is unavailable, leave the corresponding animation target unqualified. A release may enable a qualified platform cohort only after matching platform probes and lifecycle gates. An implementation that fails the universal still fallback does not ship on that target.
