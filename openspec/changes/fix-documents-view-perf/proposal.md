## Why

With a library of 272 documents, opening or switching to the Documents view lags badly. The dominant cause is **sync bookkeeping, not rendering**: every time the Documents tab becomes active, [DocumentsView.tsx:285-286](src/components/documents/DocumentsView.tsx:285) calls `loadDocuments()`, which unconditionally fans out to `registerExistingFilesSyncLazy(docs)` ([fileSyncRegistration.ts:145](src/lib/fileSyncRegistration.ts:145)) for **every document in the library, every single time**, serially:

- For each of the 272 docs with an existing `fileId`, it does `manifest.getAllFiles().find(f => f.id === fileId)` — an O(n) linear scan repeated once per document, so O(n²) work over the file manifest just to confirm files that were already registered.
- It then calls `publishDocument(doc)` ([documentReplication.ts:151](src/lib/documentReplication.ts:151)) for every document **unconditionally**, even when nothing about the document changed since the last publish — writing to the shared Yjs `documents` map 272 times in a row.
- Each of those 272 Yjs writes fires the map's `observe()` handler ([documentReplication.ts:99](src/lib/documentReplication.ts:99)), which enqueues `handleRemoteDocument(key)` for that key on the progressive sync scheduler — so the app also processes 272 "remote" document events generated by its own local re-publish of unchanged data.
- All of this runs as one long serial `for` loop awaited on the main JS thread with no batching/yielding, so it blocks interaction (scrolling, clicking, typing) for as long as it takes to churn through the whole library.

Separately, the two default list layouts (compact card list and compact table) render every document in `sortedDocuments` via `.map()` with no virtualization/windowing, which adds further rendering cost on top of the sync stall, though it is the smaller factor for a library this size.

The `get_documents` backend command already returns lightweight summaries (content/metadata nulled out), so the backend query itself is not the bottleneck — this is a client-side sync-loop and rendering problem.

## What Changes

- **Sync (primary fix):** Stop re-running full per-document sync registration on every Documents-tab activation.
  - Skip `publishDocument(doc)` when the document's clock (`dateModified`/`dateAdded`) hasn't changed since the last successful publish, using the existing `syncClockCache` (already used for the remote-replay path but not the local-publish path).
  - Replace the per-document O(n) `manifest.getAllFiles().find(...)` scan with a single O(n) index/Set built once before the loop, so manifest membership checks are O(1) per document.
  - Only run the full existing-files sync pass (`registerExistingFilesSyncLazy`) once per app session (already the behavior of the boot-time `hydrateStartupDocuments` path via `runDeferredSyncSetup`) rather than again on every `loadDocuments()` call triggered by tab activation; subsequent `loadDocuments()` calls should only sync documents that are new or whose sync-relevant fields changed since the last pass.
  - Chunk/yield the remaining per-document sync work (e.g. via `requestIdleCallback`/microtask batching) so any unavoidable work doesn't block the main thread in one uninterrupted pass.
- **Rendering (secondary fix):** Virtualize the two default Documents view list layouts (compact card list and compact table/grid) using `@tanstack/react-virtual` (already a project dependency) so only rows near the viewport are mounted.
- Memoize the per-view filter-count computation (`filterCounts` in `CompactLibraryView`) and other O(n) scans over `documents`/`sortedDocuments` that currently re-run on every render.
- Preserve existing behavior: selection (click, shift-click, ctrl/cmd-click, long-press on mobile), context menu, keyboard navigation, sort/filter controls, and cross-device sync correctness (new/changed documents still propagate) must continue to work unchanged.
- No backend Rust/IPC/database changes — `get_documents` already returns summaries; both fixes are client-side.

## Capabilities

### New Capabilities
- `document-library-list-rendering`: Defines the performance/virtualization behavior for the Documents view library list (windowed rendering, row recycling, and interaction parity) so large libraries stay responsive.

### Modified Capabilities
- `yjs-sync-performance`: Adds requirements that document sync registration/publish work must skip unchanged documents, avoid O(n²) manifest scans, and not re-run in full on every Documents-tab activation.

## Impact

- Affected code:
  - [src/stores/documentStore.ts](src/stores/documentStore.ts) — `loadDocuments()`'s unconditional call to `registerExistingFilesSyncLazy(docs)`.
  - [src/lib/fileSyncRegistration.ts](src/lib/fileSyncRegistration.ts) — `registerExistingFilesSync()`'s per-document loop (manifest scan, hashing, publish).
  - [src/lib/documentReplication.ts](src/lib/documentReplication.ts) — `publishDocument()` (add clock-based skip) and its `documentsMap.observe()` handler.
  - [src/components/documents/DocumentsView.tsx](src/components/documents/DocumentsView.tsx) — `CompactLibraryView`'s card-list and table renderers, and the `filterCounts` computation.
- Dependency: `@tanstack/react-virtual` (already in `package.json`, not yet used in this file).
- No changes to Rust backend, database queries, or IPC commands.
- Risk: sync-skip logic must not suppress legitimate propagation of new/changed documents to other devices — clock comparison must be conservative (publish whenever in doubt). Virtualization must preserve scroll position, selection state, and keyboard/touch interactions exactly.
