## Context

Three independent bugs/gaps in the Documents library and priority popup, found by tracing the reported symptoms into `src/components/documents/DocumentsView.tsx`, `src/components/documents/usePriorityPopup.tsx`, `src/stores/documentStore.ts`, and `src-tauri/src/database/repository.rs`:

1. **Extract-count drift**: `repo.create_extract()` (`src-tauri/src/database/repository.rs:1598-1657`) inserts into `extracts` but never updates `documents.extract_count`. The frontend compensates with an in-memory-only patch (`patchDocumentExtractCount` in `src/api/extracts.ts:116-123` → `documentStore.patchExtractCount`), which is silently clobbered by `mergeDocumentSummary()` (`src/stores/documentStore.ts:66-75`, `{...existing, ...summary}`) on the next `loadDocuments()`/`loadDocumentsPage()` call — i.e. every collection switch, page load, or app restart. The Compact View "Has extracts" signal filter (`doc.extractCount > 0`, `DocumentsView.tsx:375`) and the EXTRACTS column both read this same stale field, so both under-report. `delete_extract` (`repository.rs:2012-2014`) has the mirror problem.
2. **Priority popup zero-value bug**: `resolveDisplaySlider()` (`usePriorityPopup.tsx:45-52`) uses `(doc.prioritySlider ?? 0) > 0` to decide whether a slider value is "set." A document whose user explicitly set priority to `0` (the lowest preset) is indistinguishable from a document that was never touched, so the popup reseeds to the neutral default of `50` instead of `0`. This reproduces in Document view, Queue, and library rows alike, since all three call sites (`DocumentViewer.tsx:3506`, `ReviewQueueView.tsx:812`, `DocumentsView.tsx:1028`) go through the same helper.
3. **No sort shortcuts for extracts/flashcards in the Compact sidebar**: `DocumentSortKey` already includes `"extracts"` and `"cards"` (`src/utils/documentsView.ts:4`) and both List view's column headers and the Compact "Sort by" `<select>` already expose them. The Compact View's left sidebar "Signals" section (`DocumentsView.tsx:2486-2507`) only exposes them as *filters* (`compactFilter`), not as quick sort shortcuts, and there's no equivalent affordance in Grid view.

## Goals / Non-Goals

**Goals:**
- Extract counts persisted in `documents.extract_count` are always correct after create/delete, independent of in-memory patches.
- Alt+P popup seed value always matches the document's actual current priority, including an explicit `0`.
- Users can quick-sort by Extracts/Flashcards from the Compact View sidebar without losing the existing Signals filters, with a UI treatment that makes "sort" visually distinct from "filter."
- Sort state (key + direction) behaves consistently whether triggered from Compact sidebar, List column headers, or the Compact "Sort by" dropdown; Grid view respects whatever sort is active.

**Non-Goals:**
- Reworking the priority scoring algorithm (`priorityScore`/`userIntent` formulas) — only the popup's *seed value* is in scope.
- Adding a dedicated sort control to Grid view beyond making it respect the shared `sortKey`/`sortDirection` state (no new Grid-specific UI).
- Changing the semantics of the existing Signals filters (Has extracts / Has cards remain single-select filters).

## Decisions

- **Persist extract_count via direct SQL update on write, not a recount trigger.** In `create_extract`, add `UPDATE documents SET extract_count = extract_count + 1 WHERE id = ?` in the same transaction as the insert; mirror with `- 1` (floored at 0) in `delete_extract`. Rejected alternative: a SQL trigger on the `extracts` table — triggers work but are harder to reason about/test in this codebase (no existing precedent; only FTS triggers exist), and an explicit same-transaction update keeps the invariant visible at the call site next to the insert/delete it depends on.
- **One-time backfill migration for existing drift.** Existing databases likely already have `documents.extract_count` out of sync with real `extracts` rows (this is the exact symptom in the bug report — 272 docs, EXTRACTS column showing 0). Add a migration that runs `UPDATE documents SET extract_count = (SELECT COUNT(*) FROM extracts WHERE extracts.document_id = documents.id)` once, mirroring the pattern already used in `kindle_clippings.rs:1024`.
- **Keep the frontend in-memory patch (`patchDocumentExtractCount`) as an optimistic-update layer, not a source of truth.** Once the backend persists the count, the patch and the reloaded value should agree, so `mergeDocumentSummary()`'s `{...existing, ...summary}` overwrite becomes harmless instead of destructive. No frontend store logic changes are required beyond this becoming correct as a side effect of the backend fix.
- **Backend schema genuinely conflates "unset" and "explicit 0" today — confirmed by reading `src-tauri/src/models/document.rs:33-34,88-89,190-191`.** `priority_rating`/`priority_slider` are non-nullable `i32` columns defaulting to `0` on document creation, so a document that has never had its priority touched and one whose priority was deliberately set to `0` via the popup are stored identically. This means the popup-reseed bug cannot be fixed as a pure frontend truthiness check — the information needed ("was this ever explicitly set?") doesn't exist yet.
  - **Original plan (rejected during implementation):** make `priority_slider`/`priority_rating` nullable (`INTEGER` allowing `NULL`), `NULL` = "never explicitly set", via a 12-step SQLite table rebuild. Prototyping this migration showed it re-activates the `documents.category FOREIGN KEY REFERENCES categories(id)` constraint (SQLite enforces it on the freshly-built table even though it was effectively dormant on the original), which breaks both existing tests and real user rows whose `category` is a free-form tag rather than a `categories(id)` row. That data-integrity risk on upgrade was unacceptable for a UX fix.
  - **Decision: add a single boolean sentinel column `priority_explicitly_set` (NOT NULL INTEGER DEFAULT 0) via plain `ALTER TABLE ... ADD COLUMN` — no table rebuild, no FK re-activation.** `0` means "never explicitly set", `1` means the user committed a priority via `update_document_priority`. This carries the exact same information a nullable column would (the spec's "NULL means unset" is satisfied by `priority_explicitly_set = 0`), without altering the existing priority columns or their constraints. `update_document_priority` flips it to `1` on every commit; `resolveDisplaySlider` honors `priority_slider` as-is (including `0`) when it is set, falling back to the rating bucket / neutral midpoint only when it is not. Existing rows default to `0`, matching the documented trade-off (a pre-migration document a user genuinely set to priority `0` will show the neutral seed once, then self-correct the next time they touch it) — called out explicitly as a one-time, low-blast-radius trade-off.
- **Sort shortcuts as a visually distinct row below Signals, not merged into it.** Add a small "Sort by" affordance (e.g. two compact buttons "Extracts ↕" / "Flashcards ↕") in the Compact sidebar, using button styling distinct from the Signals filter buttons (different icon treatment, e.g. a sort/arrow icon vs. the existing signal icon, and no filter-style count badge) so the two are not visually confusable. Clicking sets `sortKey` to `"extracts"`/`"cards"` and toggles `sortDirection` on repeat clicks (matching the List view header click behavior), rather than introducing a separate, third sort-state model.

## Risks / Trade-offs

- [Backfill migration cost on very large libraries] → Runs once, single `UPDATE ... subquery`; acceptable for local SQLite libraries in the hundreds-to-low-thousands of documents range this app targets. No mitigation needed beyond running it as a normal migration step.
[Nullable `priority_slider`/`priority_rating` migration touches every document row and every read/write path in `repository.rs` (10+ call sites listed in Context) plus the Rust struct types and TS `Document` type] → Mitigated by making the columns nullable additively (existing non-null reads/writes keep working via `.unwrap_or(0)`/`?? 0` at call sites that don't need the new distinction, e.g. sorting/filtering by extract/card counts are unaffected), and by scoping this migration narrowly to just the two priority columns rather than a broader schema rework.
- [Pre-migration documents genuinely set to priority 0 by a user will show the neutral (50) seed once after migration] → Accepted trade-off, called out in the Decisions section; self-corrects the next time the user touches that document's priority. No better alternative exists since the current schema has already destroyed the "was this explicit" signal for existing rows.
- [New sidebar sort buttons add visual clutter to an already dense Compact sidebar] → Mitigated by keeping them small, secondary in visual weight to filters, and only two entries (Extracts, Flashcards) rather than exposing the full sort-key list in the sidebar.

## Migration Plan

1. Backend: add `extract_count` increment/decrement to `create_extract`/`delete_extract`, plus a migration backfilling existing rows. Ship and verify via the existing repository/integration tests plus a manual check against the 272-doc "Personal" collection scenario from the bug report.
2. Frontend: fix `resolveDisplaySlider`; verify Alt+P in Document view, Queue, and library rows against a document with priority explicitly set to 0.
3. Frontend: add sort shortcuts to Compact sidebar; verify sort state parity across Compact/List/Grid.
4. No rollback complexity beyond standard migration rollback (the backfill is idempotent and can be re-run safely).

## Open Questions

- None outstanding — the nullable-column approach in Decisions resolves the only ambiguity (backend "unset vs. explicit zero" distinction) found during investigation.
